# ADR-002: Contract-first: OpenAPI як єдине джерело правди, клієнти генеруються
Статус: Прийнято
Дата: 2026-11-27

## Контекст

Один бекенд обслуговує два мобільні клієнти — нативний Android і Flutter ([ADR-004](ADR-004-two-mobile-clients.md)). API нового продукту проєктується з нуля, без сумісності зі старим додатком ([ADR-007](ADR-007-independent-product.md); [docs/PROJECT.md](../PROJECT.md), розділи 2, 7). Агенти не спілкуються напряму, а обмінюються артефактами (розділ 6), тож API має бути зафіксований в артефакті, з якого працюють усі три потоки розробки.

## Рішення

`contracts/openapi.yaml` (OpenAPI 3.1) — єдине джерело правди API для бекенду й обох клієнтів (розділ 8). Будь-яка зміна API починається зі зміни контракту, а не коду.

- Контракт змінює лише `architect`; приклади — у `contracts/examples/`. Зміна контракту — перша задача в `tasks.md` зміни OpenSpec ([ADR-008](ADR-008-openspec.md)) і завжди окремий PR, що мерджиться раніше за реалізацію (розділ 12).
- CI проганяє Spectral і перевірку ламаючих змін oasdiff проти `main`; техлід апрувить PR з контрактом; ламаючі зміни потребують нової версії API.
- Код генерується openapi-generator: бекенд — `kotlin-spring` (лише інтерфейси й DTO, `interfaceOnly=true`), Android — `kotlin` з `jvm-retrofit2` і `kotlinx_serialization`, Flutter — `dart-dio`. Документація — Redocly або Scalar у `docs/api/`; mock-сервер — Prism.
- Згенерований код вручну не редагується.
- springdoc на бекенді — лише для перевірки, не джерело правди (розділ 3).
- Правила контракту: `operationId`, опис, приклади й усі коди відповідей для кожного ендпоінту; помилки у форматі RFC 9457 Problem Details (`type`, `title`, `status`, `detail`, `code`); курсорна пагінація (`cursor`, `limit`, `nextCursor`); дати ISO 8601 UTC; ідентифікатори — UUID-рядки; версія в шляху `/api/v1/...`.
- Спільна модель кімнати — `contracts/room-model.schema.json` (JSON Schema, посилання з OpenAPI; розділ 11.1).

## Наслідки

Позитивні:

- Бекенд, Android і Flutter розробляють фічу паралельно: клієнти — проти mock-сервера Prism до готовності бекенду.
- Обидва клієнти отримують мережеві моделі з одного контракту, що зменшує розбіжності між ними.
- Бекенд реалізує згенеровані інтерфейси; контрактні тести перевіряють кожну відповідь на відповідність `openapi.yaml` (розділи 9, 13).
- Ламаючі зміни виявляються в CI до merge.

Негативні / ризики:

- Контракт — вузьке місце: кожна зміна API проходить через `architect` і апрув техліда; dev-агенти зупиняються, якщо контракту бракує.
- Реалізація не може почати фічу, поки PR з контрактом не змерджено.
- Результат залежить від генераторів openapi-generator для трьох цілей; ручні правки згенерованого коду заборонені, обходити обмеження генератора доводиться в контракті або в обгортках.
- Ламаючі зміни вимагають нової версії API, тож дизайн контракту варто продумувати наперед.

## Розглянуті альтернативи

- **Code-first: контракт генерується springdoc з коду бекенду.** Відхилено: джерелом правди стала б реалізація бекенду, а клієнти не могли б стартувати до її готовності. springdoc залишено лише для перевірки.
- **Ручні API-клієнти на кожній платформі за документацією.** Відхилено: два незалежні клієнти вели б моделі вручну, і розбіжності з бекендом і між клієнтами виявлялися б лише під час інтеграції.
