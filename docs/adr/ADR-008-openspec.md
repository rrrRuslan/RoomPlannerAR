# ADR-008: Специфікації й зміни ведуться в OpenSpec
Статус: Прийнято
Дата: 2026-11-27

## Контекст

Мета продукту — функціональний паритет з iOS-референсом: кожна функція референсу має відповідник у специфікації й перевіряється паритетним тестом ([docs/PROJECT.md](../PROJECT.md), розділ 1). Два клієнти реалізують одну поведінку незалежно ([ADR-004](ADR-004-two-mobile-clients.md)), а агенти працюють від артефактів і не повинні вгадувати ([ADR-005](ADR-005-agentic-development.md)). Тому специфікація має бути платформонезалежною, перевірюваною і жити поруч з кодом.

## Рішення

Специфікації можливостей і зміни ведуться в [OpenSpec](https://github.com/Fission-AI/OpenSpec) (`@fission-ai/openspec`, OpenSpec 2.x, schema `spec-driven`) у каталозі `openspec/` монорепозиторію ([ADR-001](ADR-001-monorepo.md); розділи 4, 5, 7, 12).

- `openspec/specs/<capability>/` — живий опис того, що продукт уже вміє; наповнюється лише під час archive змін.
- `openspec/changes/<change>/` — `proposal.md`, дельта-специфікації, `design.md` за потреби, `tasks.md`; завершені — у `changes/archive/`.
- Цикл: `/openspec-propose` (`architect`) → апрув техліда → `/openspec-apply-change` (dev-агенти у своїх worktree) → `openspec validate <change> --strict`, ревʼю, QA → `/openspec-archive-change` після merge (`docs-writer`).
- Етап 0: `spec-analyst` створює зміну `add-<capability>` на кожну можливість референсу; затверджує техлід.
- Вимоги описують поведінку, а не реалізацію, не залежать від платформи й мають сценарії GIVEN / WHEN / THEN для успіху, помилок і офлайну. Текст — українською; заголовки й ключові слова (`Requirement`, `Scenario`, `SHALL` / `MUST`, GIVEN / WHEN / THEN) — англійською.
- `tasks.md` групується за агентами; зміна API-контракту — перша задача ([ADR-002](ADR-002-contract-first-openapi.md)).
- Тікет у Jira лише посилається на зміну; назва зміни входить у гілку, тікет і PR. Назви тестів містять можливість і вимогу для матриці паритету `docs/qa/parity-matrix.md`.
- На одну можливість одночасно — не більше однієї активної зміни.
- Без зміни OpenSpec, звичайним тікетом: баги, що не змінюють описаної поведінки, рефакторинг, оновлення залежностей.
- CI: `openspec.yml` проганяє `openspec validate --strict` для змінених змін і специфікацій (розділ 14).

## Наслідки

Позитивні:

- Специфікація лежить у репозиторії, змінюється й ревʼюється через PR разом з кодом.
- Трасування: вимога → задача → тест → колонка матриці паритету.
- `openspec/specs/` завжди відповідає реалізованому, а заплановане видно в `openspec/changes/`.
- Агенти працюють зі специфікаціями й змінами через skills `/openspec-*` у Claude Code.

Негативні / ризики:

- Кожна фіча, що змінює поведінку, потребує пропозиції й апруву техліда до старту розробки.
- Обмеження «одна активна зміна на можливість» може серіалізувати роботу над однією можливістю.
- OpenSpec активно змінюється; команди й поля конфігурації треба звіряти з актуальною версією (розділ 17).
- Змішування мов (український текст, англійські ключові слова) вимагає дисципліни; `validate --strict` перевіряє формат.

## Розглянуті альтернативи

- **Специфікації в довільному Markdown у `docs/`.** Відхилено: немає фіксованого формату вимог і сценаріїв, валідації, дельт і циклу propose → apply → archive, який відділяє реалізоване від запланованого.
- **Специфікації лише в Jira.** Відхилено: специфікація жила б поза репозиторієм і не змінювалася б у тому ж PR, що й код (розділ 15); у прийнятому процесі тікет лише посилається на зміну OpenSpec (розділ 12).
