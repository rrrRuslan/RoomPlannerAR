# ADR-001: Монорепозиторій для всіх компонентів
Статус: Прийнято
Дата: 2026-11-27

## Контекст

Продукт складається з бекенду (Kotlin, Spring Boot), нативного Android-клієнта (Kotlin, Jetpack Compose), Flutter-клієнта (iOS + Android), а також API-контракту, специфікацій OpenSpec і документації ([docs/PROJECT.md](../PROJECT.md), розділ 1).

API ведеться за підходом contract-first ([ADR-002](ADR-002-contract-first-openapi.md)): зміна `contracts/openapi.yaml` тягне генерацію коду для бекенду й обох клієнтів і перевірку всіх трьох компонентів (розділи 8, 14). Розробку ведуть паралельно кілька AI-агентів, кожен у своєму worktree і зі своїми каталогами ([ADR-005](ADR-005-agentic-development.md), розділи 4, 6).

## Рішення

Усі компоненти живуть в одному git-репозиторії зі структурою з розділу 5 docs/PROJECT.md:

- `contracts/` — `openapi.yaml`, `room-model.schema.json`, приклади;
- `openspec/` — специфікації й зміни ([ADR-008](ADR-008-openspec.md));
- `backend/`, `android/`, `flutter_app/`, `infra/`, `.github/workflows/`;
- `docs/` — PROJECT.md, ADR, згенерована документація API, QA, runbooks;
- `reference/ios-app/` — старий iOS-додаток як read-only git submodule ([ADR-007](ADR-007-independent-product.md));
- `.claude/` і `CLAUDE.md` — конфігурація агентів, hooks, permissions, skills.

Кожен агент пише лише у свої каталоги (розділ 6); `contracts/` змінює тільки `architect`, згенерований код вручну не редагується. Обмеження задаються permissions і hook `PreToolUse` у `.claude/settings.json`.

CI на GitHub Actions запускає лише ті пайплайни, чиї шляхи змінилися в PR; зміна `contracts/**` запускає пайплайни контракту, бекенду, Android і Flutter (розділ 14).

## Наслідки

Позитивні:

- Зміна контракту, бекенду й клієнтів проходить через один репозиторій і один CI; `contract.yml` після генерації клієнтів збирає всі три компоненти.
- Генерація з `contracts/openapi.yaml` пише прямо в `backend/`, `android/core/network/` і `flutter_app/packages/api_client/` (розділ 8), без окремої публікації клієнтів.
- Агенти бачать контракт, специфікацію, ADR і код в одній робочій копії; документація оновлюється в тому ж PR, що й код (розділ 15).
- Одна конфігурація агентів, hooks і permissions для всього проєкту.

Негативні / ризики:

- В одному репо поєднуються різні тулчейни (Gradle, Flutter, Xcode для збірки iOS на Mac / macOS runner); CI має фільтрувати пайплайни за шляхами, інакше кожен PR збирає все.
- Будь-яка зміна `contracts/**` запускає всі пайплайни компонентів.
- Розмежування доступу між агентами тримається на permissions і hooks, а не на правах до окремих репозиторіїв.
- Паралельні агенти працюють з одним `main`: потрібні окремі worktree і rebase на свіжий `main` перед PR (розділ 12).
- Попри один репозиторій, зміна контракту завжди йде окремим PR, що мерджиться раніше за реалізацію (розділ 12).

## Розглянуті альтернативи

- **Полірепо: окремий репозиторій на бекенд, Android, Flutter і контракт.** Відхилено: зміна контракту вимагала б узгоджених PR у кількох репозиторіях і публікації згенерованих клієнтів; агентам довелося б працювати з кількома робочими копіями, а один CI не міг би перевірити всі три компоненти разом.
- **Окремий репозиторій для контрактів і специфікацій, решта — разом.** Відхилено: контракт і специфікація — головні джерела правди для коду (розділ 1), і їх відокремлення від коду ускладнює перевірку генерації та збірки в одному CI.
