# ADR-007: Новий незалежний продукт з власним бекендом; старий iOS-додаток лише функціональний референс і буде знятий з App Store
Статус: Прийнято
Дата: 2026-11-27

## Контекст

У техліда є існуючий iOS-додаток (Swift, ARKit, RoomPlan) з власним бекендом. Потрібен продукт з нативним Android- і Flutter-клієнтом, що досягає функціонального паритету з цим додатком, включно з AR ([docs/PROJECT.md](../PROJECT.md), розділи 1, 2).

Поки старий застосунок доступний в App Store, схожий новий застосунок від того самого розробника ризикує відхиленням як дублікат за App Store guideline 4.3 (розділ 2.1).

## Рішення

Створюємо новий незалежний продукт. Старий iOS-додаток — лише функціональний референс, а не частина продукту (розділи 2, 2.1).

- **Ідентичність:** нові bundle ID і applicationId, нові записи в App Store Connect і Google Play.
- **Бекенд і дані:** новий власний бекенд; жодного доступу до даних і API старого додатку; без міграції й синхронізації.
- **Акаунти:** нові; користувачі старого додатку реєструються заново.
- **Код референсу:** підключається як read-only git submodule `reference/ios-app` ([ADR-001](ADR-001-monorepo.md)); референсна версія фіксується git-тегом на старті, подальші зміни не відстежуються. Агенти читають його лише для розуміння поведінки; архітектура, моделі даних і API проєктуються заново ([ADR-002](ADR-002-contract-first-openapi.md)).
- **Що можна брати:** дизайн, іконки, ілюстрації (як основу), тексти, 3D-моделі (USDZ конвертуються в glTF/GLB); Swift-код ARKit / RoomPlan — як основу iOS-частини плагіна `ar_bridge`, адаптовану під `RoomModel` ([ADR-004](ADR-004-two-mobile-clients.md)).
- **Що не переносять агенти:** секрети, ключі підписування й облікові дані; їх техлід налаштовує окремо для кожної платформи.
- **Поза обсягом:** будь-які зміни в старому iOS-додатку; сумісність даних, акаунтів чи API з ним.
- **Зняття з App Store:** старий застосунок знімається з продажу в App Store до подання нового на ревʼю або одночасно з релізом (розділ 2.1, фаза 4 у розділі 18); у нотатках для App Review зазначається, що новий продукт його замінює.

## Наслідки

Позитивні:

- Архітектура, API й дані нового продукту проєктуються з нуля, ідіоматично для Kotlin і Dart, без обмежень сумісності.
- Немає робіт з міграції й синхронізації даних і акаунтів.
- Поведінка референсу стає специфікацією нового продукту ([ADR-008](ADR-008-openspec.md)) і основою паритетних тестів.

Негативні / ризики:

- Користувачі старого додатку мають зареєструватися заново; їхні дані не переносяться.
- Поки старий застосунок доступний у сторі, новий ризикує відхиленням за guideline 4.3.
- Точний момент зняття старого застосунку з продажу ще не визначено (розділ 18).
- Зміни старого додатку після фіксації тегу не потрапляють у референс.
- Повний паритет потребує спершу описати всю поведінку референсу як специфікацію (фаза 1).

## Розглянуті альтернативи

- **Оновити старий iOS-додаток і його бекенд, додавши Android-клієнти.** Відхилено: зміни в старому додатку і сумісність з його API поза обсягом (розділ 2); новий API проєктується з нуля за контрактом ([ADR-002](ADR-002-contract-first-openapi.md)).
- **Новий продукт з міграцією акаунтів і даних старого додатку.** Відхилено: сумісність даних і акаунтів поза обсягом; користувачі реєструються заново (розділ 2.1).
- **Залишити старий застосунок в App Store паралельно з новим.** Відхилено: ризик відхилення нового застосунку як дубліката за guideline 4.3.
